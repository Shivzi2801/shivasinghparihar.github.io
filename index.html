PMOS Permission-Aware AI Knowledge Assistant

A working AI knowledge assistant that answers with evidence — and only from what the person asking is actually allowed to see.

After 10 years shipping products in regulated environments — where access control was never optional — I kept seeing the same failure in AI knowledge tools: they answer confidently regardless of who's asking or what that person is permitted to know. PMOS is a working vertical slice built to fix that. It retrieves an organization's knowledge, filters it by tenant and role before generation, cites its sources, and says "I don't know" when the evidence can't support a safe answer — verified today against a synthetic demo corpus, not yet a validated commercial product.

◎Vision
Enterprise knowledge, with evidence you can trust.

A working MVP that retrieves an organization's own knowledge, filters it by what the requesting user is actually permitted to see, and answers with a cited, inspectable source — never a confident guess. This is a product hypothesis about trust in AI answers, verified today against a synthetic demo corpus — not yet a validated commercial product.

⚠Problem
An AI answer is only useful if the person asking is actually allowed to have it.

Most enterprise knowledge assistants are built to answer confidently regardless of who's asking. In real organizations, most valuable knowledge is permissioned — by tenant, by role, by policy. My working hypothesis: knowledge-work teams need answers that are provably scoped to what the asker is authorized to see — and honest when they aren't, instead of hallucinating past the gap.

✦Why it matters
01
Trust requires proof
Every answer is grounded in a cited, inspectable source — never a confident string with nothing behind it.
02
Access is not optional
The same question returns a different — correct — answer depending on who's asking, and returns nothing when no permitted evidence exists.
03
Built by a practitioner
Not a wrapper around a chat API — a tenant-aware ingestion pipeline, ACL-filtered retrieval, and a grounded-answer path built end to end.

Scar Tissue — The ESG Dashboard That Shipped and Went Unused
ESG Materiality Platform · Deloitte USI · 2022–2023
What Happened
Midway through the ESG Materiality Platform build, I scoped a benchmarking dashboard that let clients compare their materiality scores against industry peers. In discovery sessions and demos, stakeholders responded enthusiastically — "that would be really useful," "love that." I treated that as demand signal and built it into the sprint plan.

The feature shipped on schedule. Three months later, usage was near zero. When I went back to the same stakeholders, the honest answer was: they'd been polite in demos, not committed. No one actually owned the job of running peer benchmarks — it was interesting, not essential.
What I Changed
I now distinguish between enthusiasm and intent in every discovery session. Enthusiasm is easy to manufacture in a demo. Intent shows up when you ask "who would use this weekly and what would they do differently because of it?" — and get a specific, named answer.

I also introduced a lightweight commit test before any new feature enters scope: at least one named user agrees to be interviewed post-launch specifically about that feature. If no one will sign up for that conversation, the feature isn't ready to build.

The mistake cost one sprint. The framework it produced has saved several since.

The Problem

Enterprise knowledge is scattered across support tickets, runbooks and internal documentation. Retrieval alone doesn't solve it, because an assistant answering inside an organisation has to resolve four questions at once, not one:

  • Is this information relevant to what was asked?
  • Is this information accessible to this particular user?
  • Can the answer be traced back to evidence the user can open?
  • What should happen when the evidence isn't available at all?

An enterprise AI assistant should not only know an answer. It should know whether the user is allowed to see the evidence behind it.

I have not validated this as a market problem. It is the problem I chose to build against, drawn from ten years of shipping in regulated environments where access control was never optional.

Product Thinking — The MVP Decision

Rather than building a broad enterprise AI platform, I scoped one narrow vertical slice and made it work end to end: ingest → permission-aware retrieval → grounded answer → evidence.

The reasoning was about where the risk actually sat. Generating fluent text is close to a solved problem and would have proved nothing. The hard part — the part that decides whether an enterprise can deploy this at all — is generating a useful answer without crossing the user's knowledge boundary. So that is what I built first, and what the demo is designed to interrogate.

  • Permission before generation — authorization is part of retrieval, not a filter applied afterwards.
  • Evidence before confidence — a claim the user cannot trace is not an answer.
  • Abstain rather than invent — a safe failure mode is a feature, not an error state.
  • Tenant isolation by construction — not by convention or by careful querying.
  • Permission changes shouldn't force re-embedding — authorization state and content identity are separate concerns.
  • A demonstrable slice beats feature breadth — one honest end-to-end path is worth more than a list of disconnected AI features.

What I Built

One workflow. Three trust boundaries.

The clearest way to show what PMOS does is to ask it one question twice, changing nothing but who is asking.

01 — Authorization Boundary
Same question. Different authorization boundary.
The Viewer cannot access the restricted evidence. The Admin can. The question does not change.
02 — Inspectable Evidence
Evidence is inspectable, not decorative.
The answer can be traced to the source title, excerpt, citation marker, document and chunk metadata.
03 — Tenant Isolation
Tenant isolation survives retrieval.
An administrator in GLOBEX cannot retrieve ACME's knowledge.

Both tenants hold synthetic demo corpora: 12 documents for ACME and 3 for GLOBEX, deliberately on unrelated subjects so that isolation shows as a question being genuinely unreachable rather than a tenant simply being empty.

Product Decisions & Tradeoffs
Decision 01
Permission before generation
Generating an answer first and filtering afterwards risks exposing restricted information — and the exposure happens before the filter runs. Authorization is therefore applied during retrieval, so restricted evidence never reaches the generation step at all.
Decision 02
Abstention over unsupported answers
An enterprise assistant needs a safe failure mode. When permitted evidence is missing or inaccessible, PMOS says so explicitly instead of assembling something plausible from whatever ranked highest. The tradeoff is a system that visibly declines more often — which I treat as the correct direction for this use case.
Decision 03
ACL changes without re-embedding
A permission change does not change what a document says. Treating authorization state as separate from content identity means updating who may read a document costs a payload rewrite rather than re-embedding unchanged content — which matters as soon as a corpus is large enough for embedding cost to be real.
Decision 04
Deterministic embeddings for the demo
The current slice exists to validate retrieval, authorization and product behaviour — not embedding quality. A deterministic provider keeps the demo free of external API cost and dependency and makes it reproducible. The tradeoff is explicit: these embeddings carry no semantic signal, so ranking leans on a keyword reranker, and production-grade semantic quality is not something this build has demonstrated.
Decision 05
Vertical slice over feature breadth
A working end-to-end security-aware flow is more useful for validation — and more honest in a portfolio — than a broader collection of disconnected AI features. It also means the gaps are visible rather than hidden behind surface area.

Business Model — Hypothesis

The shape I would test first is a per-agent SaaS subscription with a minimum seat commitment — the unit a support leader already budgets in, and the one that scales with the value being delivered rather than with query volume.

The value argument I would need to prove: if the system reduces escalations, shortens agent resolution time, or lowers onboarding effort, the subscription can be justified against the operational cost of running support. That is a value hypothesis — I have not measured any of those effects, and the price above is arithmetic, not evidence.

Next validation step: interview support leaders and agents, quantify escalation and search friction against their current baseline, then test willingness to pay.

What I'd Build Next

Zendesk or Confluence integration with incremental sync, identity and group synchronization, and real ACL capture from the source system — replacing the demo corpus, whose permissions are declared rather than captured.
P1

Multi-turn conversations with source continuity across turns, plus a feedback loop so agents can mark where an answer helped or missed.
P2
Evaluation harness
Measurable grounding, retrieval and abstention quality, plus permission-leakage tests run as a gate. Today those behaviours are verified by direct scenario testing, not scored.
P2
Production LLM and semantic embeddings
Move off deterministic demo embeddings and the extractive composer once retrieval quality is measurable — so the upgrade can be evaluated rather than assumed.

These are plans, not capabilities. None of the above exists in the current build.

Closing

PMOS is intentionally small today. The product question I wanted to answer first was not “Can I build an AI assistant?” It was “Can I build one that knows what a user is allowed to know, shows its evidence, and fails safely when it cannot?”
